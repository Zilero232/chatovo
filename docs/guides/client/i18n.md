# i18n

Every user-visible string goes through **`use-intl`** in the web app and **`next-intl`** (built on it) on the site, in every locale. The list is `LOCALES` in `@chatovo/config` — en, ru, uk, es, pt, de, fr, tr, pl — with `LOCALE_NAMES` (each language in its own words) and `OPEN_GRAPH_LOCALES`; both apps read it from there. The kit imports from `use-intl`, which works under either provider. No string maps, no hard-coded text in components.

## Where the messages live

Each app keeps its own `shared/i18n/locales/<locale>/<namespace>.json` — one file per namespace, the same set of files and the same keys in every language. A new key goes into all nine files at once, translated, never left in English. `DEFAULT_LOCALE` is per app in `shared/i18n/config.ts`: `en` in the web app, `ru` on the site.

| Where | Namespaces |
| --- | --- |
| `apps/client/web` | `admin`, `app`, `auth` (also account deletion and the legal links), `common`, `room`, `social` |
| `apps/landing` | `marketing.json`, whose top-level keys are the namespaces: `home`, `features`, `download`, `downloadApp`, `changelog`, `about`, `support`, `legal`, `notFound` |
| `packages/ui-kit` | `ui` — the kit's own strings (`messages/<locale>.json`, exported as `uiMessages`) |

Each app spreads `uiMessages.<locale>` into its messages (`locales/<locale>/index.ts`), so a kit component's `useTranslations('ui')` works in either. A string used only by a kit component goes in `ui`; anything app-specific stays in the app.

`messages.d.ts` in each app types the messages (and, on the site, the locale union) from the English files; nothing generates it, and it rarely changes. ESLint ignores that file because it augments `AppConfig` (of `use-intl` in the web app, `next-intl` on the site), which only an `interface` can do.

## Reading them

- Client components: `useTranslations('<namespace>')`, plus `useFormatter` and `useLocale` when you need them.
- Server components (the site only — the web app has none): `getTranslations` from `next-intl/server` in an async component, or `useTranslations` in a non-async one. The site is server components by default, and its client components receive only the `ui` namespace — pass them their strings as props.

## Locales and the URL

- **The web app** keeps the locale as a user setting (`entities/app/locale`, stored in localStorage; Settings → General); the URL carries none. On the first launch it is `detectLocale(navigator.languages)` — `@formatjs/intl-localematcher` picks the closest supported language (pt-BR → pt, be → ru), else English. Each locale is its own chunk, loaded by `loadMessages` and read with `use()` under a Suspense boundary in `AppProviders`; switching runs in a transition, so the old language stays on screen until the new one has loaded.
- **The site** carries it in the path through next-intl routing (`proxy.ts`, `shared/i18n/routing.ts`): Russian is the default with no prefix, every other language lives under its code (`/en`, `/de/features`), `/ru/...` redirects to the bare path. The bare home page (`/`, Russian) sends a first-time visitor to the closest language of the browser once per session (`HomeLocaleRedirect`); a link that already carries a language is never redirected; the header has a language picker; the sitemap and every page's `alternates` list all nine languages. Build links with `localizeMarketingPath`, read the locale in a page with `readPageLocale` — [apps/landing/CLAUDE.md](../../../apps/landing/CLAUDE.md).

## The tests keep the locales honest

`shared/i18n/_tests/` in each app holds the guards, and they run in `bun run test`:

- `locale-parity.test.ts` — every locale has the same namespaces and keys as `en`, and no message of 24+ characters is left in English.
- `error-locales.test.ts` (web) — every server error code from `@chatovo/schemas` has a message in every locale; a missing one would ship as a blank error toast.
- `unused-messages.test.ts` — a key nothing reads any more fails the suite, so delete the key with the code that used it.
