# i18n

Every user-visible string goes through **`next-intl`**, in both locales. No string maps, no hard-coded text in components.

## Where the messages live

Each app keeps its own `shared/i18n/locales/{en,ru}/<namespace>.json` — one file per namespace, the same set of files and the same keys in both languages. `LOCALES` and `DEFAULT_LOCALE` are in `shared/i18n/config.ts`.

| Where | Namespaces |
| --- | --- |
| `apps/web` | `admin`, `app`, `auth` (also account deletion and the legal links), `common`, `room`, `social` |
| `apps/site` | `marketing.json`, whose top-level keys are the namespaces: `home`, `features`, `download`, `downloadApp`, `changelog`, `about`, `support`, `legal`, `notFound` |
| `packages/ui-kit` | `ui` — the kit's own strings (`messages/{en,ru}.json`, exported as `uiMessages`) |

Each app spreads `uiMessages.<locale>` into its messages (`locales/<locale>/index.ts`), so a kit component's `useTranslations('ui')` works in both. A string used only by a kit component goes in `ui`; anything app-specific stays in the app.

`messages.d.ts` in each app is generated: don't edit it by hand. It is also why ESLint ignores that file — next-intl augments its own module there, which only an `interface` can do.

## Reading them

- Client components: `useTranslations('<namespace>')`, plus `useFormatter` and `useLocale` when you need them.
- Server components: `getTranslations` from `next-intl/server` in an async component, or `useTranslations` in a non-async one. The site is server components by default, and its client components receive only the `ui` namespace — pass them their strings as props.

## Locales and the URL

- **The web app** keeps the locale as a user setting (`entities/app/locale`, stored in localStorage); the URL carries none.
- **The site** carries it in the path through next-intl routing (`proxy.ts`, `shared/i18n/routing.ts`): Russian is the default with no prefix, English lives under `/en`, `/ru/...` redirects to the bare path. Build links with `localizeMarketingPath`, read the locale in a page with `readPageLocale` — [apps/site/CLAUDE.md](../../../apps/site/CLAUDE.md).

## The tests keep the locales honest

`shared/i18n/_tests/` in each app holds the guards, and they run in `bun run test`:

- `locale-parity.test.ts` — `en` and `ru` have the same namespaces and the same keys.
- `error-locales.test.ts` (web) — every server error code from `@chatovo/schemas` has a message in both locales; a missing one would ship as a blank error toast.
- `unused-messages.test.ts` — a key nothing reads any more fails the suite, so delete the key with the code that used it.
